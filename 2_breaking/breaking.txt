PANDAS BREAKING-POINT TEST
--------------------------

Commands run:
python scripts\pandas_pgn_test.py "Z:\lichess_db_standard_rated_2026-06.pgn\lichess_db_standard_rated_2026-06.pgn"

(pandas_pgn_test.py launches pandas.read_csv() with no chunksize in a child
process, polls the child's RSS every 5s via psutil, and writes
pandas_output.txt / pandas_error.txt / pandas_memory_log.txt /
pandas_summary.txt)

Observed result:
UnicodeDecodeError after 346.63 seconds: 'utf-8' codec can't decode byte
0x93 in position 0: invalid start byte

pandas.read_csv() was reading the whole 8.913 GiB file into a single-column
DataFrame (one row per physical PGN line) with the C engine. It ran for
~5.75 minutes before hitting a decode error on a non-UTF-8 byte pulled in by
the read-ahead buffer — by that point its own process RSS had already
climbed past 8.7 GiB (see memory log below), i.e. pandas had already loaded
essentially the entire file into memory before the C parser ever got to
validate encoding, which is exactly the "loads everything into RAM first"
failure mode this phase is meant to demonstrate.

Peak memory / timing (from pandas_summary.txt):
  status=ERROR
  exit_code=3
  elapsed_seconds=350.14
  raw_file_size_gib=8.913
  peak_pandas_rss_gib=8.795

Memory growth sample (from pandas_memory_log.txt, full log has one line
every 5s for the whole run):
  elapsed=0.1s   pandas_rss=0.019 GiB  memory_percent=61.3%
  elapsed=60.1s  pandas_rss=0.653 GiB  memory_percent=72.3%
  elapsed=145.1s pandas_rss=1.283 GiB  memory_percent=83.1%
  ...  (climbs steadily to peak_pandas_rss_gib=8.795 GiB just before the
        UnicodeDecodeError at elapsed=346.63s)

pandas_error.txt is intentionally empty: the child process catches the
exception inside run_pandas_child() and reports it to stdout
(pandas_output.txt) rather than letting it propagate to stderr, so there is
no separate traceback to capture.

COMMAND-LINE VS. SPARK AGGREGATION (same computation, two ways)
-----------------------------------------------------------------
(a) Command line (1_profile/profiling.txt): total games counted with
    `zstdcat ... | grep -c "^\[Event "` = 86,483,328, computed in 14m24s
    on a single core, single machine.

(b) PySpark (3_scaling/analysis.py, run on Dataproc): the same file, read
    from GCS and grouped by time-control category, gives per-category game
    counts that sum to 86,458,368 (Blitz 40,105,287 + Bullet 31,670,872 +
    Rapid 14,234,716 + Classical 383,331 + Unknown 64,162 -- see
    3_scaling/run_1worker.log). The ~25K-game (0.03%) gap is expected: the
    Spark job additionally requires a parseable WhiteElo and a decisive-or-
    draw Result to keep a row, so it drops the small number of games with
    missing rating tags or an ongoing/aborted ("*") result that the raw
    grep -c count doesn't filter out.

Both tools independently land on essentially the same ~86.5M-game total
for the same file -- a real cross-check between the two toolchains, not
just two unrelated numbers. The wall-clock contrast is the actual point of
this comparison: the CLI count is a single grep pass with no aggregation
logic (14m24s); the Spark job does a full parse plus five separate
aggregations (groupBy, join, window function, Spark SQL) over the same
file and finishes the whole pipeline, cluster included, in well under an
hour even on the smallest (1-worker) cluster -- see 3_scaling/scaling.txt
for the full scaling comparison.
