# First-Move Advantage in Online Chess

CS 131 Final Project — GitHub repo: https://github.com/TrtQu/First-Move-Advantage-in-Online-Chess

## Question

Does White's first-move advantage in online chess change with player skill
(Elo) and with time control (bullet/blitz/rapid/classical)? We answer this
using the full Lichess "standard rated games" dump for June 2026.

## Dataset

[Lichess standard-rated games, June 2026](https://database.lichess.org/standard/lichess_db_standard_rated_2026-06.pgn.zst)
— 26 GB compressed (`.pgn.zst`), 86,483,328 games, 1,730,301,832 lines
decompressed. Comfortably past both Excel's 1,048,576-row limit and this
project's 5 GB / 50M-row floor.

## Repo layout

- [`1_profile/`](1_profile/) — Phase 1: CLI-only profiling of the raw
  dataset (`du`, `wc -l`, `head`/`tail`, `cut`, `sort | uniq -c`, `awk`,
  `grep -c`, every command timed).
- [`2_breaking/`](2_breaking/) — Phase 2: reproducing the point where Excel
  and pandas both fail on this dataset, with scripts, logs, and memory

- [`3_scaling/`](3_scaling/) — Phase 3: the same aggregation run as a

## Phase 2 — Breaking point

Full write-up: [`2_breaking/breaking.txt`](2_breaking/breaking.txt)

- **Excel**: a 400 MB / 10,050,001-row CSV (generated by streaming the live
  Lichess feed with [`fast_excel_stream.py`](2_breaking/scripts/fast_excel_stream.py))
  exceeds Excel's 1,048,576-row worksheet cap.
- **pandas**: `pandas.read_csv()` on the full 8.9 GiB decompressed PGN
  ([`pandas_pgn_test.py`](2_breaking/scripts/pandas_pgn_test.py)) climbed to
  8.795 GiB of process RSS and crashed with a `UnicodeDecodeError` after
  ~346 seconds — by which point it had already pulled essentially the whole
  file into memory, which is exactly the failure mode this phase is meant
  to demonstrate.

## Phase 3 — Scaling with PySpark on Dataproc

Full write-up: [`3_scaling/scaling.txt`](3_scaling/scaling.txt)
Job script: [`3_scaling/analysis.py`](3_scaling/analysis.py)

The full dataset is read directly from `gs://promising-cairn-501617-g0-cs131-lichess/`
(never copied into the repo). The job defines an explicit schema, transforms
raw PGN tags into Elo brackets and time-control categories, groups by Elo
bracket and by opening, ranks top openings per time control with a window
function, joins the aggregated stats against a skill-tier reference table,
caches the parsed DataFrame across three reused actions, and cross-checks
one aggregation with Spark SQL.

| Workers | Runtime |
|---|---|
| 1 | 3288.01s (54.8 min) |
| 2 | 2675.11s (44.6 min) |
| 4 | 2177.79s (36.3 min) |

Runtime drops ~18.6% per doubling, not the ~50% linear scaling would
predict — because `.zst` isn't a splittable codec, the initial
decompress/record-split step always runs as a single task regardless of
cluster size, forming a fixed floor under the total runtime (a live
demonstration of Amdahl's Law). Only the repartitioned aggregation stages
speed up with more workers. Full explanation and per-run logs in
`3_scaling/scaling.txt`.

## Findings

White's win rate rises steadily with player skill: from **29.7%** at the
lowest Elo bracket (400) up to **52–53%** at master level (2400+), while
Black's win rate falls correspondingly (61.6% → ~40%). The first-move
advantage is real, but it's earned — weaker players convert it far less
often than strong players do. By time control, White's overall edge is
fairly stable (~49.5–50% across bullet/blitz/rapid/classical), so skill
level matters far more to the advantage than pace of play.
